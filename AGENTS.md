# Второй мозг — схема

Система по паттерну Андрея Карпатого «LLM Wiki»: знания компилируются один раз в вики и поддерживаются актуальными, а не пересобираются из сырья на каждый запрос. Ты (LLM) — поддерживающий вики. Человек — куратор источников, задаёт вопросы и ведёт проекты.

Эта папка — общий мозг для любого агента: Codex, Claude Code, Cursor, Gemini CLI и других. Правила живут здесь, в `AGENTS.md`; `CLAUDE.md` и `GEMINI.md` только подключают этот файл. Скиллы лежат в `.agents/skills/` (`.claude/skills` — ссылка туда же).

## Скиллы
Каждый скилл — папка `.agents/skills/<name>/` с файлом `SKILL.md` (открытый формат Agent Skills). Если твой агент подгружает скиллы сам — пользуйся ими как обычно. Если нет — **когда задача подходит под скилл, сначала прочитай его `SKILL.md` целиком и следуй ему**, а нужные `references/` открывай по ссылкам из него.

| Скилл | Когда |
|---|---|
| `c4-project` | Человек просит завести, пересмотреть или закрыть проект. Только по прямой просьбе. |
| `c4-brainstorm` | Задача мутная или есть несколько путей: зафиксировать результат, ограничения, критерии и выбрать подход. |
| `c4-plan` | Работа требует фаз, архитектуры или плана. |
| `c4-cook` | Реализовать план по фазам или маленькую понятную правку. |
| `c4-scout` | Найти нужные файлы в мозге или репозитории перед работой. |
| `context4` | Работа с подключёнными сервисами (CRM, задачи, почта и др.) через Context4. |
| `context4-setup` | Подключить Context4 к агенту и сервис к Context4. |
| `context4-workflows` | Задача сразу по нескольким сервисам (CRM + звонки, CRM + мессенджер…). |

Обычный путь большой задачи: `c4-brainstorm` → `c4-plan` → `c4-cook`; `c4-scout` — внутри любого шага. Человек может назвать скилл как угодно («c4-plan», «/c4-plan», «сделай план») — это один и тот же скилл.

## Первый запуск
Мозг свежий, если в `projects/` нет ни одного проекта и в `log.md` есть только запись `init`. Тогда, в первом ответе сессии (что бы человек ни написал первым):

1. **Познакомь коротко**, простыми словами, без терминов — человек может быть не программистом. 4–6 строк:
   - это твой второй мозг: папка, которую я веду за тебя, и она остаётся твоей, даже если сменишь ИИ;
   - присылай мне в чат что угодно — статью, ссылку, заметку, расшифровку, файл — и скажи «запомни»: я сохраню и разложу по проектам;
   - спрашиваешь «что у меня про X?» — отвечаю по твоим записям со ссылками;
   - у каждого дела — свой проект; в каждой сессии работаем с одним проектом.
2. **Предложи завести первый проект:** «Давай заведём первый проект — то, над чем ты сейчас работаешь или что давно хочешь начать. Я задам вопросов десять, можно отвечать голосом и сумбурно». Согласился — запусти `c4-project`. Отказался — предложи начать с материала: «Тогда пришли мне статью или заметку и скажи "запомни"».
3. Если человек сразу пришёл с конкретной задачей — сначала короткое знакомство одной-двумя строками, потом его задача. Проект не навязывай.
4. Запиши в `log.md`: `## [YYYY-MM-DD] onboarding | Первый запуск`. После этого мозг уже не свежий — знакомство не повторяй.

## Три слоя
1. `raw/` — сырьё. Сюда агент **сам** сохраняет дословно всё, что человек прислал в чат. После сохранения файл **неизменяем**: не правь, не перефразируй, не удаляй.
2. `wiki/` — твой слой. Markdown-страницы, которые ты создаёшь, обновляешь и перелинковываешь. Человек их только читает.
3. Эта схема (`AGENTS.md`) — правила. Вы дорабатываете её вместе.

Человек руками в папки ничего не кладёт: всё приходит через чат, раскладываешь ты.

## Структура: проект — раздел в каждой папке
Каждый слой разбит по проектам. Раздел `general` — для всего, что не относится к одному проекту.
```
raw/<project>/                       сырьё проекта, дословно, с шапкой метаданных
raw/general/                         сырьё вне проектов
wiki/<project>/sources/              по странице на источник (саммари + ссылка на raw)
wiki/<project>/concepts/             идеи, темы, методы
wiki/<project>/entities/             люди, компании, инструменты, продукты
wiki/<project>/syntheses/            сохранённые ответы, сравнения, анализ
wiki/general/{sources,concepts,entities,syntheses}/   общее знание и то, что нужно нескольким проектам
projects/<project>/                  паспорт проекта (см. «Проекты»)
plans/<project>/  plans/general/     планы (скилл c4-plan)
outputs/<project>/ outputs/general/  результаты (не источник знаний)
index.md                             каталог: проекты и страницы вики по разделам
log.md                               хронология операций (append-only)
```
- `<project>` — slug проекта из `projects/`, одинаковый во всех папках. Разделы `raw/<project>/`, `wiki/<project>/…`, `plans/<project>/`, `outputs/<project>/` создаёт `c4-project` при заведении проекта.
- Раздел выбирается по закреплённому проекту сессии (см. «Текущий проект сессии»). Без проекта — `general`.
- Знание, нужное нескольким проектам, живёт в `wiki/general/` с перечнем проектов в `projects:`. Страница одного проекта, которая стала нужна второму, остаётся на месте: второй проект ссылается на неё. Переносить в `general` — только с ОК человека (предлагает lint).

## Формат файла в raw
Имя: `raw/<project>/YYYY-MM-DD-<slug>.md`, slug kebab-case латиницей. Текст — **дословно**, как прислал человек или как скачан со страницы. Шапка:
```yaml
---
title: <заголовок или первая строка>
project: <slug | general>
kind: article | link | note | transcript | chat | doc | file
source: <URL | chat | исходное имя файла>
captured: YYYY-MM-DD
---
```
Нетекстовый файл (PDF, картинка, аудио) сохраняй рядом как есть — `raw/<project>/YYYY-MM-DD-<slug>.<ext>` — и клади к нему файл метаданных `…<slug>.meta.yaml` с теми же полями. Текст, который ты из него извлёк (OCR, расшифровка), — отдельный `.md` рядом с той же шапкой и `source:` на исходный файл.

## Формат страницы вики
Имена файлов: kebab-case, латиницей. Фронтматтер:
```yaml
---
title: ...
type: source | concept | entity | synthesis
project: <slug | general>   # раздел, в котором лежит страница
projects: []                # все проекты, которым она нужна (для general — обязательно)
tags: []
sources: []                 # ссылки на wiki/<project>/sources/* или raw/<project>/*
created: YYYY-MM-DD
updated: YYYY-MM-DD
---
```
Ссылки между страницами — `[[wiki/<project>/concepts/x]]`. Утверждения подкрепляй ссылкой на источник. Противоречия не прячь — помечай `> ⚠ Противоречие:`.

## Операции
**Ingest — «запомни»** (человек прислал в чат текст, ссылку, файл или голосовую расшифровку и говорит «запомни», «сохрани», «обработай» — или просто прислал материал без задачи):
1. **Проект.** Возьми закреплённый проект сессии. Не закреплён — спроси: «В какой проект сохранить? Активные: `a`, `b` — или в общее (general)?»
2. **Сохрани дословно** в `raw/<project>/` по формату выше. Ссылка — скачай текст страницы и сохрани его (в `source:` — URL); не открылась — сохрани ссылку и то, что человек о ней написал, и скажи об этом. Видео и аудио — сначала расшифровка любым доступным инструментом. Файл — сохрани как есть плюс извлечённый текст.
3. **Обсуди коротко** 3–5 ключевых выводов. Если человек торопится — пропусти и просто разложи.
4. **Разложи по вики:** `wiki/<project>/sources/<slug>.md`, затем обнови или создай затронутые concept/entity-страницы в разделе проекта (общее — в `wiki/general/`). Один источник часто трогает 10–15 страниц.
5. **Отчитайся одной строкой:** что сохранено и сколько страниц обновлено.
6. Обнови `index.md`, допиши `log.md` проекта и корневой `log.md`: `## [YYYY-MM-DD] ingest | Название`.

**Query**: читай `index.md`, затем страницы раздела текущего проекта, потом `wiki/general/`, потом других проектов. Отвечай с цитированием. Ценный ответ сохраняй в `wiki/<project>/syntheses/` и логируй (`## [дата] query | Вопрос`).

**Lint** (по запросу «lint»): противоречия, устаревшие утверждения, страницы-сироты, упомянутые но не созданные концепты, отсутствующие перекрёстные ссылки, пробелы данных, проекты без движения дольше их `review_by`; файлы в `raw/` без страницы в `wiki/…/sources/`; файлы не в своём разделе или без шапки; страницы одного проекта, которые стали нужны нескольким (кандидаты в `general`). Только предлагай — переносы делай с ОК человека. Лог: `## [дата] lint | ...`.

## Текущий проект сессии
Человек может держать несколько сессий одновременно, каждая со своим проектом. Поэтому проект выбирается **на сессию, в разговоре**, и никуда в общий файл не записывается.

1. **Определи проект в начале работы.** Признаки, по порядку: человек назвал проект; задача однозначно про один проект из «Активных» в `index.md`.
2. **Не понятно — спроси один чёткий вопрос**, прежде чем что-то создавать или менять:
   «С каким проектом работаем? Активные: `a`, `b`, `c` — или без проекта (general)?»
   Не угадывай. Чистые вопросы к вики (query) можно делать без проекта.
3. **Проект выбран → закрепи его.** Прочитай `project.yaml`, `README.md`, хвост `log.md` и `decisions.md` проекта и выведи отдельной строкой, дословно:

   > **ВАЖНО: Для данной сессии закреплён проект `<slug>`.**

   С этого момента всё по проекту пишется только в его разделы: `raw/<slug>/`, `wiki/<slug>/`, `plans/<slug>/`, `outputs/<slug>/`, `projects/<slug>/`.
4. **Без проекта → тоже закрепи:** «**ВАЖНО: Для данной сессии проект не закреплён — работаем в разделе general.**» Тогда всё пишется в разделы `general`.
5. **Держи закрепление.**
   - Повторяй строку «ВАЖНО: …» в начале каждого ответа, в котором создаёшь или меняешь файлы, и после любого сжатия или потери контекста.
   - Перед записью файла проверь путь: он в разделе закреплённого проекта (или в `wiki/general/`, `index.md`, `log.md`). Путь в раздел чужого проекта — стоп и вопрос.
   - Если ты не уверен, какой проект закреплён (длинная сессия, сжатый контекст), — не угадывай, спроси снова.
6. **Смена проекта — только явно.** Если задача уехала в другой проект — спроси: «Это уже проект `x`. Переключаемся?» После «да» выведи новую строку «ВАЖНО: Для данной сессии закреплён проект `x`.» Чужие проекты без спроса не трогай.

## Проекты
Проект — это то, ради чего человек вообще копит знания. Поэтому проект заводится осознанно и с полным контекстом.

- **Проекты никогда не создаются автоматически.** Ни при ingest, ни при query, ни при планировании. Если материал похож на новый проект — максимум предложи одной строкой: «Похоже на отдельный проект. Завести через `c4-project`?» — и жди ответа.
- Создание, пересмотр и закрытие проекта — только через скилл `c4-project`. Он проводит интервью и не создаёт проект, пока не выяснит главное: зачем, цель, критерий готовности, первый шаг.
- Знания проекта — в `wiki/<slug>/`, сырьё — в `raw/<slug>/`, планы — в `plans/<slug>/`, результаты — в `outputs/<slug>/`. В `projects/<slug>/` — только паспорт. Активные проекты перечислены в `index.md`.

### Паспорт проекта (фиксированная структура)
```
projects/<slug>/
├── project.yaml   метаданные: статус, даты, теги, люди, репозитории, сервисы, страницы вики
├── README.md      суть: зачем, цель, критерий готовности, ограничения, риски, next actions
├── interview.md   дословные ответы человека из интервью (не перефразировать, только дописывать)
├── decisions.md   журнал решений: дата, решение, почему, какие были варианты (только дописывать)
├── log.md         хронология работы по проекту (только дописывать)
├── notes/         рабочие заметки и черновики проекта
└── assets/        рабочие файлы проекта: логотипы, макеты, выгрузки, референсы
```
- В корне паспорта — только эти пять файлов и две папки. Подпапки внутри `notes/` и `assets/` — по смыслу, kebab-case латиницей.
- **Метаданные только в `project.yaml`**, в `README.md` их не дублируй. Статус, даты, ссылки меняются там.
- Материал, из которого надо извлечь знания, идёт через «запомни» в `raw/<slug>/` и `wiki/<slug>/`, а не в `assets/`. В `assets/` — то, что проекту нужно как рабочий файл.
- Код проекта, если он большой, живёт в своём репозитории; путь или URL записывается в `project.yaml → repos`.
- Важное решение по проекту (выбор подхода, отказ от идеи, смена цели) — строка в `decisions.md`. Любая заметная работа — строка в `log.md` проекта; в корневой `log.md` идёт одна строка со ссылкой на проект.

## Подключение сервисов (MCP)
Когда проекту нужно подключить внешний сервис — CRM, таск-трекер, почту, мессенджер, GitHub и т. п. — или человек говорит «подключи MCP / подключи <сервис>»:

1. **Сначала проверь Context4.** Открой каталог подключений `https://ctx4.me/docs/connectors.json` (для человека — `https://ctx4.me/apps`) и найди сервис. Каталог читай каждый раз заново — он меняется.
2. **Сервис есть → сразу ставь через Context4** по скиллу `context4-setup` (MCP `https://ctx4.me/mcp`, вход через браузер). Отдельно проверять статус и набор действий не нужно. Работай с сервисом по скиллу `context4`, с несколькими сразу — по `context4-workflows`. Если Context4 уже подключён — не переподключай, используй.
3. **Сервиса в каталоге нет → скажи об этом прямо** и спроси, как быть: подождать, использовать другой способ подключения или обойтись без него. Другой MCP-сервер без согласия человека не ставь.
4. **Запиши результат в проект:** что подключено и через что — в `project.yaml → services`, само решение — в `decisions.md`.
5. Логины, пароли и токены в чат не проси и в файлы не пиши — авторизация только через окно входа сервиса.

## Планы
Планы реализации делает скилл `c4-plan` в `plans/<project>/<YYMMDD-HHMM>-<slug>/` (без проекта — `plans/general/`). Скилл планирования проект не создаёт.

## Правила
- Сохранённое в `raw/` не правь и не удаляй.
- Не удаляй страницы и проекты без ОК человека — помечай `status: deprecated` (страницы) или `status: dropped` (проекты).
- Каждая операция заканчивается обновлением `index.md` и `log.md`.
- Не выдумывай за человека: чего не знаешь о его целях и проектах — спроси или пометь `❓ не выяснено`.
- Масштаб: до ~100 источников хватает `index.md`; дальше предложи локальный поиск (например, qmd).
